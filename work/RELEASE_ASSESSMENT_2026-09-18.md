## 二、发版进度：距下一个版本号还有多远

### 2.1 当前位置

`0.3.2-alpha`（pyproject）——但 `__init__.py` 还是 `0.3.0`，**版本号本身就不同步**（Astra P15 指出过）。所以第一步不是"发新版"，是**统一现有版本号**。

### 2.2 建议的下一个版本：`0.4.0`

理由：
- 这不是补丁。schema 从 v1 → v3（**破坏性存储变更**，旧程序拒绝读新库）、新增 `term_slots`/`entity_region_facts`/`review_*` 五张表、MCP 协议从硬编码 `2024-11-05` 到协商 `2025-11-25`、review 权威从 JSON 迁 SQLite、`--layered` 行为从"只打印"变为"真落库"。按 semver 语义这些都是 **minor 级**（对既有 API 的消费者是加法+明确拒绝，不是删函数），但**数据格式**是 major 级变更——alpha 阶段用 minor 表达即可。
- 不建议 `1.0.0`：B8 未达标（见下），且 P21 消费方同步未做，"稳定"宣称不成立。

### 2.3 距离 `0.4.0` 发布还差什么（按阻塞程度）

| 项 | 阻塞性 | 状态 | 剩余工作 |
| :--- | :--- | :--- | :--- |
| 版本号统一 | **阻塞** | ❌ | `__init__.py` 0.3.0 → 与 pyproject 一致（一行改动） |
| 存量库迁移文档 | **阻塞** | ❌ | `README`/发布说明必须写明：升级前需 `migrate_store` v2→v3 + `web-rebuild`；旧构建拒绝读新库是预期行为；备份路径 |

### 2.4 结论：距离与路径

**距 `0.4.0` 发布：约一步之遥（1-2 个工作日）。**

必做的只剩三件小事：
1. **版本号统一**（一行）；
2. **迁移说明文档**（升级路径 + 备份要求 + 旧库不兼容声明）；
3. **（强烈建议）`sekaisync migrate` CLI 命令**，让存量用户能自助升级。

这三件完成后即可发 `0.4.0`，**发布说明中明确**：新 schema 的性能收益（browse 62x、search 830x）、逐区服事实与防剧透过滤（region 必填）、MCP 兼容面（2025-11-25/2025-06-18 反报价）、i18n 增量修复。

**距 `1.0.0`（正式稳定）：还差 B8 收口与 P21**——真实客户端互操作矩阵、Windows 之外的平台验证、发布故障点全矩阵、以及 DSH/WinUI 对新 schema 的消费适配。这些需要外部条件（真实客户端、多平台机器），不是本地能单方面关闭的。
